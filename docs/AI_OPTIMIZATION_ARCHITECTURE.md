# Radiocity AI and Optimization Architecture

## Purpose

Radiocity places data-driven optimization above source-specific physical models. Physics remains the authority for evaluating candidate thermal operating points; LightGBM is a surrogate, and PSO searches a bounded decision space. The current implementation is a simulation architecture, not a hardware controller.

## Current dynamic flow

```text
At simulation timestep t
    ↓
Update thermal temperature and incident thermal power
Update RF power density
    ↓
Build current thermal and RF channel states
    ↓
Generate physics-derived training samples
    ↓
Fit LightGBM surrogate for useful thermal power
    ↓
PSO searches a bounded spectral operating window
    ↓
Evaluate candidate through the physics/system model
    ↓
Accept only if configured thermal constraint passes
    ↓
Thermal + RF harvesting → repository → load allocation
    ↓
Record source state, harvested energy, unmet load, and storage state
```

## LightGBM role

The current LightGBM model is trained on samples generated by the existing physics model. It approximates the model's useful-power calculation over features including source/receiver temperatures, spectral-window limits, capture and conversion efficiencies, emissivity, view factor, and area.

This is a **physics-derived surrogate**, not a model trained on independent measured data. It can speed up candidate evaluation but inherits the assumptions and errors of its source model. Predictive accuracy must be evaluated on held-out physics-generated samples before claiming a meaningful speed or accuracy advantage.

The current pipeline retrains the surrogate during each optimization call. It does not yet perform a time-series forecast of future source conditions; it reacts to the source state supplied at the current timestep.

## PSO role

Particle Swarm Optimization searches bounded spectral operating variables for thermal channels. The candidate is subsequently checked against the system/physics model and the configured maximum-temperature constraint. This is not equivalent to dynamically actuating a physical spectral filter.

Before reporting an optimum, verify the optimizer bounds, candidate feasibility, surrogate error, convergence across seeds, and comparison against a grid-search or fixed-window baseline. Report predicted and physics-validated power separately.

## Dynamic source profiles

`DynamicSourceProfile` supports deterministic functions of simulation time for thermal source temperature, thermal incident power density, RF power density, and a solar-irradiance field. The current intelligent simulation consumes the thermal and RF fields. It records the solar field when supplied, but it does not yet route that value through a solar/PV conversion model.

Profiles are synthetic unless explicitly constructed from sourced data. They are suitable for repeatable stress tests and controlled comparisons, not as direct evidence of field performance.

## Repository and distribution

The simulation routes useful output from the currently implemented thermal and RF paths into a common finite-capacity energy repository, then allocates energy to requested loads. Metrics include source-specific useful power, delivered energy, unmet demand, repository energy, and state of charge. Storage losses, charging/discharging power limits, realistic battery dynamics, and fully consistent source-to-load accounting still require further verification.

## Reinforcement learning

RL is a **future research pathway**, not part of the current implementation. It should be considered only after a verified simulator, stable baselines, realistic constraints, and a reproducible reward/evaluation design exist.

## Explicitly not implemented

- Real-time physical actuation or sensor feedback.
- An end-to-end solar/PV channel in the intelligent simulation.
- A validated near-field thermal-radiation/NF-TPV solver.
- Hardware-controlled vacuum-gap or spectral-filter adjustment.
- Reinforcement learning.
- Empirical validation of end-to-end device performance.
